# The instruction-set layer

How `crates/isa` is built: what every instruction set's crate offers, and
the conventions they share. `turbonop-isa` (`crates/isa/core`) holds the
traits; this says how crates implement them.

## Goals

Tools are written once, over any instruction set: sweeps, control-flow
graphs, cross-references, fingerprints, diffs, listings; and later
lifters into an IR, decompilers, lowering from the IR, assemblers, and
binary rewriters. Adding an instruction set means writing its crate, not
editing the tools.

## Layers

| Layer | Per instruction set | General |
|---|---|---|
| `turbonop-isa` | | the traits; flow, registers, memory, operands, text |
| each ISA's crate | decode, effects, memory, operands, text; later encode, parse | |
| `turbonop-isa-any` | | one enum over every ISA: dispatch once per buffer |
| semantics (later) | each instruction as IR, generated from formal specifications where they exist (Arm's ASL, RISC-V's Sail) | the IR |
| analysis | ABIs (per platform) | CFG, SSA, data flow, stack machines lifted to registers |
| decompiler, rewriter (later) | instruction selection, encoding choice | everything else |

A layer depends only on those above it in this table. A decoder never
depends on a container format: what an instruction names in its
container (a .NET token, a WebAssembly index, a symbol) is resolved by a
[`Resolver`] the format crate implements.

## The traits

- `Isa` (everyone): `decode`, `bytes`, `len`, `opcode`, `flow`,
  `table_targets`, `attributes`, and `context` (a function's pre-scan,
  `()` for most).
- `Registers`: every register read and written, explicit and implicit,
  typed (the ISA's own `Register`), with how a write treats the rest of
  its storage.
- `Memory`: every memory access, explicit and implicit, typed (base,
  index, displacement, segment, write-back, size).
- `Operands`: the explicit operands in a common form; each ISA's richer
  form is its own crate's, used directly by ISA-specific code.
- `Format`: text as classified tokens, in one of the ISA's syntaxes.
- Later: stack effects (WebAssembly, CIL, JVM), encoding, parsing.

## Rules

- **No strings at run time.** Opcodes, registers, operand slots, fields,
  and features are numbers (generated enums and constants). Strings
  appear only in formatting, and in parsing user input once at the
  boundary (a feature list on a command line, assembly text). Never
  `operand("rs1")`, `field("imm12")`, `contains("64bit")`, or a match
  on a mnemonic.
- **Instructions are values that hold their bytes.** `Copy`, small (a
  `size_of` assertion says how small), and decoding then re-encoding one
  gives the same bytes. Operands are read from the bytes when asked. An
  instruction doesn't hold its address; queries that need it take it.
- **Effects are complete.** Every implicit register (flags, the stack
  pointer, link registers) and every implicit memory access is reported;
  an instruction whose effects aren't all known says so
  (`Attributes::UNMODELED`). Effects are checked against an oracle.
- **Addresses are typed as addresses.** A branch's target, a
  PC-relative address, an absolute address in an instruction: each is an
  `Operand::Target`, `Operand::Address`, or a `Base::Pc`/`Base::None`
  memory access, never a bare immediate. Rewriting depends on it.
- **No allocation per instruction.** Lists are iterators; text goes to a
  `TokenSink`.
- **Generated tables are checked in**, never generated by `build.rs`:
  build time matters more than anything a build script would save. The
  generator lives in `tools/<isa>/`, and the generated file's first lines
  say which generator and which source (and version) made it, and not to
  edit it.
- **Decoders don't panic** on any bytes, and are fuzzed (`apps/fuzz`).

## Crate conventions

- Crate `turbonop-<isa>` in `crates/isa/<isa>`; `#![no_std]` with
  `alloc`; `#![warn(missing_docs)]`.
- The crate's documentation says what it decodes, what it doesn't, which
  oracle it matches, and where its tables come from.
- Files: `lib.rs` (the `Isa` value and re-exports), `decode.rs`,
  `register.rs`, `operand.rs`, `access.rs` (registers and memory),
  `flow.rs`, `format.rs`, `tables.rs` (generated); more as an ISA needs.
- Tests: unit tests of private items in `src/tests.rs`; everything else
  in one integration binary, `tests/it/main.rs` and its modules (one
  binary links once); golden files beside it in `tests/data/`.
- Licenses of what tables are generated from (`LICENSE-LLVM`,
  `LICENSE-ARM`, `NOTICE-XED`) at the crate's root, and in its
  `license` field.
