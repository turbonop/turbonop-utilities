# Stackrabbit: overnight report

2026-11-18

## Summary

M0 is done and M1 is nearly complete. Stackrabbit opens ETW traces in VS Code with:

- a CPU graph by process or thread, with a function highlighted;
- time selection;
- stack trees by process, thread, processor or stack tag, including any function's callers or callees;
- hot functions and modules;
- processes and threads tables;
- time by source line in your own editor;
- copy as Markdown;
- function names from symbols it downloads itself and saves with the trace.

Everything is pushed to the `stackrabbit` branch.

- **Import is parallel and verified.** Every stage of the import runs on every core except a short stitch. The merge is cut into time ranges built in parallel, as you suggested from the TTD indexer. On all 17 corpus traces, the result is identical to the original single-threaded import, row by row and frame by frame.
- **Reading from disk is saturated.** One thread with 16 MB reads gets 3.6–3.9 GB/s, the drive's limit, as you predicted.
- **The view renders and is tested in a real browser.** A headless-Edge harness drives it against real engine answers, and CI runs it.
- **Symbols download in the background.** They go into a WinDbg-compatible cache, 16 at a time. Trees answer at once and refresh with names when the PDBs load.
- **Two real bugs found and fixed:** stacks dropped before a processor's first context switch, and overlapping module bases in my own synthetic traces.

The machine was half busy all night with something I couldn't see per process (probably Defender or OneDrive), so the timings below are pessimistic.

**What went wrong:** the headless-Edge test harness killed only Edge's top process, and its helper processes leaked. After about 40 runs there were about 3,950 `msedge.exe` processes, which exhausted memory and hung the machine. Fixed in 01e8bf6: Edge now runs in a Windows job object that ends all of its processes, and a full harness run leaves none behind.

## Try it

The extension runs from the worktree and finds the engine in `target/`.

1. Build the engine: `cargo build --release -p stackrabbit` in `c:\jm\dev\stackrabbit`.
2. Start VS Code with the extension: `code --extensionDevelopmentPath=c:\jm\dev\stackrabbit\editors\vscode\stackrabbit`.
3. In that window, set `stackrabbit.symbolCache` to `c:\jm\symbols`. I already downloaded the symbols for `s02-cpu-spin.etl` there: 52 PDBs, 254 MB.
4. Open any `.etl` from your corpus. It imports on every core, saves `trace.etl.hxtrace` beside it, and opens from that next time.

In the view:

- **Graph:** CPU usage over time, sampled or precise (it follows Weigh), by process, by thread, or for the process picked in the Processes tab (the Graph control). Drag across it to select a range, and double-click to clear it.
- **Tree:** arrow keys move and expand, and `*` expands the hot path.
- **Functions tab:** every function and module by self and inclusive weight, with shares, sortable. Recursion is counted once, and a DLL's function is one row across processes. It follows Weigh, Frames and the time selection.
- **Copy:** the Copy button or Ctrl+C puts the selected stack row and the rows open under it, or the tab's tables, on the clipboard as Markdown, for pull requests.
- **Highlight:** click a function in the Functions tab, or press H (or Highlight) on a stack row, to draw that function's CPU over time as a line on the graph. Again to clear. On `l01` it adds 0.2–0.35 s to the graph.
- **Symbols tab:** every PDB the stacks need, most frames first, with whether its names were saved, loaded, not found or not looked for yet, and what the download did. It also lists modules with no PDB identity. Click the toolbar's symbols note to open it.
- **Line times in your source:** open a source file the trace's symbols have line info for, and each line shows its share of CPU at its end, with a heat background and a hover. Files are matched by name and as much of the path as agrees. It follows the trace view you used last; turn it off with `stackrabbit.lineHeat`. It needs private PDBs (your own code); Microsoft's public PDBs have no lines.
- **Reopens where you left it:** the settings, tab, time selection and highlighted function come back when you reopen a trace.
- **Callers and callees:** double-click a function to see its callers in the Stacks tab; untick Callers for its callees. Hover a function for its hottest call path. Hover the graph to see what was running at that moment.
- **Processes tab:** a sortable table of processes. Click one to see its threads below it, with CPU, precise running time, switches in, lifetimes and named start addresses. Both tables follow the time selection.
- **Settings:** Weigh (sampled CPU, precise CPU, waits), Group by (process, thread, processor, stack tag), Frames (function, module, address), and Callers to invert the tree.

From a terminal:

- `stackrabbit tree <trace>` prints a tree.
- `stackrabbit symbols <trace> -cache c:\jm\symbols` downloads the trace's PDBs.
- `stackrabbit bench <dir>` times import, index and trees. Add `-phases`, `-read` or `-digest` for the other measurements.
- `stackrabbit synth out.etl` writes a synthetic trace.

## Performance

Cold imports, read from disk, are 1.8 to 3.6 times faster than at the start of the night. Reopening from the index is 5 times faster and a first stack tree 3 to 4 times faster. The machine was about half busy throughout, so these numbers understate the code.

| Trace | Size | Import, before | Import, now | Reopen from index, before → now | First tree, before → now |
|---|---|---|---|---|---|
| Build, CPU (l01) | 1.0 GB | 9.4 s | 3.8 s | 0.54 → 0.10 s | 0.70 → 0.17 s |
| Build, everything (l02) | 1.8 GB | 13.3 s | 5.3 s | 0.51 → 0.10 s | 0.54 → 0.18 s |
| Registry (s06) | 1.8 GB | 7.6 s | 3.9 s | 0.36 → 0.29 s | 0.01 s |
| Memory (s08) | 1.3 GB | 5.2 s | 2.1 s | 0.03 → 0.02 s | 0.02 s |
| General profile (s04) | 6.9 GB | 47.1 s | 18.7 to 26.4 s | 0.62 → 0.28 s | 0.10 → 0.05 s |

Where the time goes now:

- **Disk:** one thread reading 16 MB at a time reaches 3.6 to 3.9 GB/s, the drive's limit. More threads don't help, as you predicted.
- **Import of the 6.9 GB trace:** decoding (on 8 threads) takes about 10 s and is now the slowest stage. Building the time-sharded parts takes about 2 s, the stitch under 1 s, and the stack joins and numbering about 3 s.
- **Decode stops scaling at about 4 threads.** On s06, decoding takes 4.3 s on 1 thread, 1.57 s on 2, 1.25 s on 4 and 1.48 s on 8. It isn't lock contention in stack interning and it isn't page faults. The likely causes are the overnight background load and the mix of performance and efficiency cores. A quiet machine or a profile of the import (below) will tell.
- **Trees:** under 0.2 s for every corpus trace, and under 50 ms for most. The 50 ms target still misses on the two big build traces (0.17 s).
- **Symbols:** downloading `s02`'s 52 PDBs (254 MB) took 23 s at 16 at a time. With symbols, the first tree answers at once and refreshes with names as the PDBs load.
- **Saved names:** a trace's function names are saved beside its index (`trace.etl.hxsyms`) and read back when it reopens, so its trees have names at once and need no PDBs. For `s02` that's 280 KB instead of 254 MB of PDBs, and a first named tree in 0.05 s instead of 0.42 s. On `l01`, saving takes 0.58 s in the background.
- **Function trees:** now as fast as by module. A shared lock taken on every frame whose PDB wasn't found was the cost, not the lookups. On `l01` by function: first tree 1.5 to 0.65 s (most of it loading PDBs), expanding 1.36 to 0.35 s, waits 1.25 to 0.37 s, and 0.31 s from saved names. The trees are byte-identical to before.
- **Tests:** the whole workspace, 1,000 tests in 72 binaries, passes in about 30 s on all cores; plus the Node tests and the Edge harness.

## Judgment calls

These are choices you may want to revisit. Each is easy to change.

- **Downloads use the system's ****curl****.** That's how `hexc` already fetches symbols, and it keeps the few-dependencies rule: no HTTP library.
- **Default symbol cache:** the `stackrabbit.symbolCache` setting, else `_NT_SYMBOL_PATH`'s cache, else WinDbg's default, `C:\ProgramData\Dbg\sym`, so a fresh install shares with WinDbg. Your `c:\jm\symbols` needs the setting, or `_NT_SYMBOL_PATH`; I didn't change your environment.
- **The engine downloads symbols only when asked.** The extension asks by default. That keeps tests and scripts from contacting Microsoft by accident.
- **The same stack can sit at more than one trie node.** The parallel import interns stacks into 64 shards, so a stack shared across shards gets a node in each. No query compares stack IDs, so no answer changes, and the index reader now accepts this. Stack IDs are numbered canonically, so they don't depend on thread count.
- **The graph uses fewer buckets than pixels when samples are sparse.** Each bucket spans at least four sampling intervals. Otherwise a short trace's graph is all spikes.
- **Graph tests rely on sample counts, not shares.** The shares shown are rounded to 4 decimals, so exact tests use counts.
- **The tree view draws DOM rows, not a canvas.** Only the visible rows exist, so it's fast, and text stays selectable and accessible. The graph is a canvas.
- **Edge's ****--dump-dom**** prints nothing in this Edge build.** The harness serves the page from its own server, and the page posts its DOM back to it.

4. **M2 has started.** The schemas captured at record time already exist: WPR's merge writes each event's `TRACE_EVENT_INFO` into the trace as EventMetadata events. Stackrabbit now reads them, keeps them in the index, names providers and events by them, and decodes any described event. Across 16 corpus traces, all 7.6 million described events decode exactly, every payload byte accounted for; the only exceptions are two known .NET quirks. Next: newer kernel event versions (s04's context switches are newer than our schema), TraceLogging's self-describing events (the corpus has almost none), and an index of event positions so a listing needn't read the whole file.
5. **Correction:** I first said s04's context switches were a newer version than our schema. Checked against Windows' own reader, all of them are version 5, 28 bytes, on every trace from this machine, and our reader reads that correctly. Our schema table only has version 2 (24 bytes). TDH on this machine has no description for version 5 at all; WPA uses its own parser. So listings show their last 4 bytes as extra. I haven't named those bytes, since nothing on the machine says what they are. Trees and graphs were never affected: the import reads context switches at offsets that version 5 shares with version 2.
6. **M2 since:** listed events show their stacks (0.18 s for 1,000 on s04), and a Regions tab reads WPA regions-of-interest files, set with `stackrabbit.regionsFile`. Clicking a region instance selects its time. Regions that use Duration or region endpoints, Parent, SelfNest or Filter are reported as unsupported rather than computed wrongly. Coverage on s04: 99.76% of events decode by something; most of the rest are kinds Windows' own TDH can't describe on this machine either. Not done: marks (none in the corpus to check against).
7. **M3 is done except mini-filters. **The new tabs are Disk, File I/O, DPC/ISR, Registry, Hard Faults, Virtual Memory, Heap, Pool and Memory. Each groups its data a few ways, follows the time selection, and lists its longest or largest items. Each reads its events on every core from only the buffers that hold them, and regroups in about 0.1 s or less. Mini-filters need a trace with their events (see Things I need from you). Along the way: Registry, Heap, Pool and more PageFault schemas, all exact on the corpus. bench -metadata now checks that kernel schemas decode exactly, which found two schema fixes. An import bug lost processes that existed only in their End events. An answer too large to send no longer hangs the request. 8. **M2: generic events.** Decoding every provider (manifest, TraceLogging, EventSource, WPP), with the event schemas captured at record time, and the recording panel.
